## 2. 裁决：是否需要全部重构？

**结论：不需要。** 全量重构四触发条件逐条检验（业界共识框架）：

| 触发条件 | wxnodus 现状 | 判定 |
|---|---|---|
| ① 架构无法承载需求演化 | 本日在**零架构破坏**下叠加：HTML 全量面板/自研 VLM 调度/OASIS 桥+三源追踪/30 天确认制/进程树回收/记忆时间衰减——全部顺 CommandBus 单一入口+组合根注入+契约测试范式落地 | ✗ 不触发 |
| ② 测试护航不足 | 3,048 用例三层契约 + 17 门禁 + ratchet 只升不降 | ✗ 不触发 |
| ③ 技术栈根基过时 | 官方 Ink 6 刚定型 / Node 22 / TS 严格 ESM / 自研零框架依赖 | ✗ 不触发 |
| ④ 重复/耦合失控 | 重复 0.66% 优秀档；耦合真实面=17 处穿透+2 巨文件——**局部债非系统债** | ✗ 不触发 |

**竞品对照（真实全量重构案例）**：codex 的 TS→Rust 重写（~95% Rust，单二进制/性能/内存安全）是**平台级动机**驱动的全量重构——动机是跨平台分发与运行时独立性。wxnodus 定位是「Windows 本机 agent CLI」：Node 运行时是产品特征（JS 生态插件面/BYOK HTTP 端点/本地 Web 技术），非负担——**无对应动机**。gemini-cli/opencode/kimi 均未做过全量重构（渐进演化）。

**渐进重构的实证效率**（本会话记录）：净删 108,133 行（ink fork 死重）+ 双组合根删除 + 版本解析统一 + handlers 11.3k→8k + DSL 外移 + 环全良性化——**全部零事故、每步门禁验证、当天可发布**。渐进路径已被证明是本仓的正确路径。
